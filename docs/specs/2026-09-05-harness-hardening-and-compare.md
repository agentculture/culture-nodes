# harness-hardening-and-compare

> Harness hardening and measurement shipped: the pi and qwen bridges (and every checkout bridge) refuse oversized bodies with a 413 instead of desynchronizing the keep-alive connection, a hung pi sync reports the timeout outcome instead of a 500, pi's read-only sandbox mode is enforced at the tool level or refused, CI proves the harness swap by running the §13 conformance kit live against fake-backed pi and qwen bridges with one shared input, deploy.sh recreates api and worker whenever the actor-token set changes, one reviewed command brings a new harness actor online after the root bootstrap, and the harness-compare workflow grades pi, qwen and colleague on the same served model across a declared task set.

## Audience

- the operator running the thor/orin/spark fleet (Ori) and the mesh agents that dispatch to it: every checkout bridge's callers (the worker), the CI reader of the adapter workflows, and the next person bringing a harness online with one command

## Before → After

- Before: today: five checkout bridges desync their keep-alive socket on a body over 8 MiB; a pi child that ignores SIGTERM surfaces as a 500; pi advertises read-only and ignores it; adapter-pi.yml and adapter-qwen.yml prove only the in-process reference actor (deviation d2 needs-follow-up); a deploy after a token change leaves api/worker stale until a hand-typed --force-recreate (#300, counted hand-turn); bringing up four actors in #294 took four hand-run scripts per host (#298); and the harness comparison is one graded run each for pi-thor and qwen-thor with no colleague in the fleet
- After: after: an oversized body gets a 413 and a closed connection on every checkout bridge; a hung pi sync returns the timeout outcome; sandbox=read-only launches pi with --tools read; CI runs the §13 kit live against fake-backed pi and qwen bridges with one shared input; deploy.sh recreates api and worker in both lanes and the README runbook agrees; deploy/prod/cutover.sh takes a host+engine from secrets to registration with --dry-run and named refusals; a colleague actor is registered on spark and the harness-compare workflow has a fifth slot; and a declared measurement manifest drives graded runs whose per-actor stats are readable per manifest version

## Why it matters

- the #294 cycle proved pi and qwen work by hand; this cycle makes the proof repeatable (CI, deploy, cutover) and the comparison a re-runnable instrument instead of an anecdote — the counted hand-turns (#118) drop by two, and 'which actor is better at what' (#28) gets its first manifest-driven data set

## Assumptions

- the fakes need less 'dynamic mode' than #297 states: the kit's -bad-input ({"repo": ...}, no instruction) is refused by the bridge's own validation ladder before any subprocess, and async is the bridge's 'async: true' flag, so a fake only has to replay a deterministic success for any instruction and hang until SIGTERM for -require-cancellation — `fake_pi.py` already has `FAKE_PI_FIXTURE` + `FAKE_PI_HANG` (29 lines) and `fake_acp_agent.py` already has `FAKE_ACP_BEHAVIOR`=ok plus a cancel path (239 lines); the harness script sets those env knobs the way the claude script sets `FAKE_CLAUDE_STREAM_DELAY`
- the comparison starts from one data point: /v1alpha1/actors/{id}/stats shows pi-thor 1 completed + 1 failed and qwen-thor 1 completed, each with one confirmed grade of 4 in category harness-compare; pi-orin and qwen-orin have zero runs (delivery doc 'orin harness parity') — a measurement needs several runs per actor per task kind, on both hosts, before a per-actor verdict is more than an anecdote
- the 45 runs cost session time, not subscription: pi, qwen and colleague all run against the local model on thor:8000, so the #48 window is untouched; the binding limit is the lobe's concurrency (one run per host at a time, per lane-capacity memory) and the operator's grading time — roughly 45 grades at a minute each
- a 413 is a contract failure, not a retry storm (challenge / adjacent-systems lens): the bridge's 413 body carries class `actor_rejected_input` and the control plane classifies from the body class (internal/actors/client.go, §13.5); the client's 4xx path was NOT read in this pass — counter-evidence to gather at plan time is one dispatch with an oversized instruction against a fake-backed bridge in the e2e stack
- colleague's mock engine exists in the installed 1.76.0 ('colleague backends list' shows mock and vllm-openai; `COLLEAGUE_ENGINE`=mock colleague whoami answers), so adapters/colleague/scripts/`run_conformance_kit.sh` can run on spark before the actor is registered; whether the bridge's vllm-openai engine reaches thor:8000 from a spark engine account is untested
