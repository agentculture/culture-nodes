# web-ui-lift

> Culture Nodes' web UI got a lift: one graph language across mesh, workflows and runs; the mesh draws the relationships the data already holds instead of a hub-and-spoke; every published workflow is readable as a graph, not only running ones; the mesh no longer replays history on arrival; and a workflow can be composed on canvas.
> instruction: Verified when every success signal (c30–c34) has a passing automated check in CI and the operator has posted the before/after screenshot review to #270; delivered as two waves on one branch, wave A = c2, c22–c26, wave B = c27 → c29 → c28.

## Audience

- Primary: the operator running the fleet from a wide display, who lives in Mesh, Runs and Design and needs to see at a glance what every machine is serving and what every workflow looks like. Secondary: a person arriving from a Jira comment to decide something (their pages — ticket, inbox, decisions — keep the treatment issue #270 gave them). Tertiary: agents reading #agent-state (webglass), which must keep asserting every fact the pixels claim.

## Before → After

- Before: Today the mesh is a hub-and-spoke that replays every historical run on arrival and says nothing about hosts, revisions or which actor runs which workflow; a graph exists only for a running workflow or an open run; workflow graphs and the mesh use two visual substrates; twelve nav destinations include three projections of one dataset and omit the authoring page; and workflows are authored only as pasted text with a read-only preview.
- After: Opening the mesh shows the org as it is right now — machines, the control plane, bridges/actors, published workflows and active runs, joined by the relationships the records hold — with no history replay; every published workflow opens as a graph from Design; the same mesh-styled node draws mesh, workflow and run views; the nav is the PRD's spine instead of twelve tabs; and a workflow can be composed on canvas, validated live, and published as an immutable version whose digest matches the CLI path.

## Why it matters

- The mesh is the product's face and the place where fleet divergence (#224: two workers, different token sets) should have been visible before a dispatch failed; a star hides exactly that. Graph-only-when-running means the design of a workflow is invisible until it costs money to run. Text-only authoring gates the product on YAML fluency, which the PRD's Design view was meant to remove.

## Non-goals

- No visual lift may break the PRD's honesty rules: everything drawn traces to a committed API row (h14 — no decorative edges, no invented attribution), reduced-motion renders one static frame, every node is keyboard-inspectable, and status is never color alone. A richer mesh draws relationships the records hold; it does not guess them.
- The human pages (/ , /tickets/:id, /inbox, /decisions) are not redesigned here beyond adopting the shared segmented-toggle control (which fixes the /decisions unstyled tab strip); their uplift stays issue #270's own lane.
- No new charting library, no mobile-first pass, no per-actor analytics (issue #28) — the lift is the graph language, the mesh's information, navigation, and the design canvas.

## Assumptions

- The mesh is a star by construction, not by data: web/src/domain/mesh.ts assembleMeshGraph emits only actor→control-plane and run→actor edges and layoutMesh puts actors on a ring around the center, so the picture carries no relationship between actors. The records already hold more: Actor rows carry kind, protocol, `endpoint_ref` (host), capabilities and metadata (web/src/api/types.ts), node-run rows carry `run_id`, `node_id` and `actor_id`, and published workflow IRs name which actor each node  — enough to draw actor↔host, actor↔workflow-node, run↔workflow and capability groupings instead of spokes.
- The mesh node style the operator likes is web/src/components/MeshCanvas.tsx: Canvas-2D on the fixed `TERMINAL_GROUND`, pre-rendered glow sprites, quantized-alpha tables, a 64-slot particle pool, entrance choreography and idle drift. Workflow graphs use a different substrate — React Flow (@xyflow/react 12) + ELK with the DOM NodeCard (224×128, light page ground, zoom detail bands per PRD §8.5). ActiveGraphCanvas.tsx already ported the mesh craft to CSS (breathing halo keyframes, one-shot pulse rings, motion gating), so a shared 'Culture node' that looks like the mesh nodes and lives on React Flow is a port, not a rewrite.
- Graphs are visible in exactly three places: the run page (routes/RunView.tsx, Graph/Timeline toggle), the Active Graphs sub-tab (ActiveGraphCanvas, only workflows pinned by a non-terminal run per domain/active-presence.ts), and the authoring preview once source parses. The 'Node Graphs' sub-tab of /graphs is misnamed: NodeGraphsPanel renders one workflow-card per `workflow_key` (versions table + recent runs list) and never a graph; the 'Nodes' sub-tab renders node-definition cards. That is why a published-but-idle workflow has no graph anywhere.
- Authoring is text-first by design: routes/AuthorWorkflow.tsx is a textarea + Upload… + Load a sample + Validate + Publish, its React Flow preview is explicitly read-only ('nothing opens on click') and every Handle in WorkflowNode.tsx is isConnectable={false}. The canvas library is not the gap — React Flow 12 supports drag, connect and selection natively; what is missing is the reverse direction (graph → IR → canonical JSON/YAML), per-kind property editing, and on-canvas compiler diagnostics (PRD Phase 3 names 'compiler diagnostics on canvas'). Generate (routes/GenerateWorkflow.tsx) is a separate page that asks an actor to propose source and never publishes.
- The header (components/Header.tsx) offers 12 destinations plus a ticket box: Your work · Inbox · Decisions | Runs · Board · Jobs · Mesh · Statistics · Node Graphs · Plan · Generate, and /workflows/new is not in the nav at all (reachable only by link). Runs, Board and Jobs are three projections of the same run/node-run rows (RunsBoard groups 'the identical GET /v1alpha1/runs rows by state'); Generate and New workflow are two halves of one Design activity. PRD §8.6 names six primary views — Design, Run, Contract, Ledger, Operations, Registry — which is a cleaner spine than the current tab strip.
- Issue #270 is the open home for UX findings and already records: /decisions renders its tab strip as unstyled buttons pinned top-left; /inbox is the most list-shaped page; neither shows where an item is in the flow. Issue #226 (mesh awareness: per-machine revision, checkout state, actor-token config, liveness) is exactly the information a non-star mesh could carry. The fixture screenshot pass (web/e2e/screenshots.spec.ts, `NODES_SHOTS`) covers 11 pages but not the mesh or active graphs, so those two have no captured evidence.
