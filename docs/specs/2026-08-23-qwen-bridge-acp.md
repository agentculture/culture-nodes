# qwen-bridge-acp

> culture-nodes officially supports Qwen Code as a fourth actor backend: adapters/qwen ships qwen-bridge, a PRD-13 actor-protocol implementation that drives Qwen Code over ACP (qwen --acp, stdio JSON-RPC), with the container image as the support contract (#113) and the configured repository as the agent's identity (#114), running on spark/thor/orin where qwen 0.22.0 already lives
> instruction: Implement adapters/qwen mirroring the sibling layout: port the shared core verbatim, write `qwen_cli` over the ACP client seam per the v1 probe contract (initialize / session/new / session/prompt / session/cancel; lenient unknown-ext handling; classify the terminal session/prompt response, never the exit code); ship the pinned Dockerfile, a CI workflow modeled on adapter-codex.yml, the unmodified conformance kit green, and the capability surface reporting measured host facts. The exported spec is the build contract; the probe at /tmp/acp-probe (this session) is the grounding evidence.

## Audience

- the spec's readers: (1) the engineer implementing adapters/qwen, (2) the operators deploying the qwen-bridge image on the spark/thor/orin fleet, (3) the control plane and the nodes CLI users who will schedule qwen actors and read its preflight capability surface

## Before → After

- Before: Qwen Code runs on the fleet as an ad-hoc session surface (spark/thor/orin, qwen 0.22.0 measured 2026-08-23) but is NOT a supported actor backend of culture-nodes: there is no adapters/qwen, no container image, no preflight capability surface - qwen invocations have no PRD-13 lifecycle (no callbacks, no idempotent replay, no cancellation, no ledger authority) and the support question 'do we officially support this agent' has no answer for qwen
- After: adapters/qwen ships qwen-bridge - a fourth PRD-13 reference implementation that passes tests/conformance unmodified, speaks the ACP client seam (initialize / session/new / session/prompt / session/cancel over stdio, classified by the terminal session/prompt response, not by exit code), boots from a pinned Dockerfile carrying node + qwen-code (#113 image contract) with the configured repository as its identity (#114), and advertises a preflight capability surface reporting measured host facts (qwen version, bundled node version, model identity, context budget)

## Why it matters

- every other schedulable backend (claude-code, colleague, codex) already has a containerized, contract-gated bridge, while qwen is the surface this repo's own session work runs on today - and the fleet is heterogeneous (measured: bundled node v22.23.2 vs v18.19.1 under the same qwen 0.22.0; models NVFP4-27B vs cortex) - so without the bridge + image + capability surface, qwen work stays unsupported, host-drift-prone, and invisible to the preflight gate

  - honesty: the adapters/qwen package mirrors the sibling layout module-for-module and the conformance kit runs against it UNMODIFIED; verify by a green tests/conformance run in the qwen adapter's CI job
- terminal-event discipline carries over: a qwen process that exits 0 without an explicit ACP terminal session event is incomplete and maps to an execution failure, never ok; only Qwen's own completed-session event (with no failure event before it) counts as a completed turn (provenance: adapters/codex/README.md load-bearing crash case + tests/`test_codex_cli.py` exit-zero rule)
  - honesty: a qwen process that exits without a terminal session/prompt event is classified incomplete and the run reports execution failure, never ok; verify by a qwen-suite test reproducing the codex-bridge crash case (exit 0, no terminal event) asserting incomplete
- host drift is measured, not assumed: the capability surface reports the bundled node version (measured drift: spark bundles v22.23.2 vs thor v18.19.1 under the SAME qwen 0.22.0), the qwen install layout, and PATH independence (qwen is not on the non-interactive ssh PATH on thor/orin - the image entrypoint must not rely on it) (provenance: ssh probes, 2026-08-23; issue #96 toolchain discipline as cited by #113)
  - honesty: the capability surface reports measured host facts - qwen version, bundled node version, model identity, context budget - not assumed defaults; verify by booting on spark/thor/orin and diffing the capability documents against the 2026-08-23 probes (node v22.23.2 vs v18.19.1; NVFP4-27B vs cortex)
- classifier grounded on MEASURED terminal shapes (challenge probe2, 2026-08-23): stopReason `end_turn` -> ok (a tool-level failure still ends `end_turn` with error null - the tool failure rides in the transcript, not the run status, as measured); stopReason cancelled -> the 13 cancellation outcome; a JSON-RPC error on the session/prompt response -> error; no terminal response (process death/timeout) -> incomplete, never ok (provenance: /tmp/acp-probe2 measurements - failing cat ended `end_turn`; cancelled list turn ended stopReason cancelled error null)
  - honesty: the measured shapes are replayable: a failing-tool turn ends `end_turn` with error null and a cancelled turn ends stopReason cancelled - verified by the qwen suite test that synthesizes both terminal responses and asserts ok and the 13 cancellation outcome respectively, and by re-running the probe2 script while the evidence exists on spark
- the bridge validates the initialize handshake before serving: the negotiated protocolVersion must be supported (measured: 1), agentInfo.version is recorded (measured: qwen-code 0.22.0), and a disagreement fails closed with a distinct message - because qwen 0.22.0 still advertises --acp alongside --experimental-acp, ACP is treated as an experimental seam: the image pins the qwen version and the conformance suite pins the handshake shape (provenance: challenge probe2 initialize response + qwen --help flag pair, 2026-08-23)
  - honesty: an unsupported handshake is refused: verified by a unit test feeding the measured initialize response with protocolVersion 2 (or agentInfo.version mismatch) and asserting the distinct refusal message before any session is served
- the 13 result payload carries a DOWNSAMPLED transcript - final assistant text, `tool_call` summaries with measured statuses (pending/`in_progress`/failed), `usage_update` totals - not the raw session/update firehose (measured ~72 notifications for one simple turn, dominated by thought chunks); the full stream is retained in the bridge's local transcript file for debugging (provenance: challenge probes 1+2 stream counts, 2026-08-23)
  - honesty: the result payload stays small: verified by asserting the payload for a turn measured at ~72 session/update notifications is <= 64 KB, against the bridge's local transcript file which retains the full stream

## Scope / boundaries

- no PRD-13 wire-protocol change: the actor contract is provider-neutral and input is opaque JSON; qwen-specific knobs (model, ACP flags, approval policy) ride on input fields the bridge itself defines, exactly as codex rides sandbox/model (provenance: api/actor-protocol/README.md + adapters/codex/README.md invocation-input table)
- the image IS the support contract (issue #113): qwen-bridge ships a pinned Dockerfile (node + qwen-code install + stdlib-only python bridge), a stated toolchain contract, a CI build, and documented build+run; a qwen backend on a host without the image is unsupported (provenance: issue #113 body via agtag issue fetch, 2026-08-23)
- the repository IS the agent's configuration (issue #114): the image carries no agent identity; at startup the bridge consumes culture.yaml + prompt file + skills from the configured repo, refuses to start with a distinct message when any leg is missing, and reports the loaded config repo + revision on the capability surface in the #96 shape (provenance: issue #114 body via agtag issue fetch, 2026-08-23)
- the ACP session mode is qwen's approval-policy surface: measured modes are plan (analyze only, no files/commands), default (approval-gated), auto-edit, auto (classifier-approved) with currentModeId defaulting to auto in a scratch session; the bridge maps input.sandbox + the preflight gate onto mode selection, fails closed (never a silently-wider mode), and reports the effective mode on the capability surface - this is the concrete candidate mapping for parked v3 (provenance: challenge probe2 session/new responses, 2026-08-23)
- qwen's model credentials and endpoint configuration are host-supplied (measured authMethods include an `OPENAI_API_KEY` env path; this fleet uses per-host settings.json endpoints) and are NEVER baked into the image or the configured repository; the capability surface reports the config source and model identity without reporting values (provenance: challenge probe2 initialize authMethods + the measured per-host model.name split, 2026-08-23)

## Non-goals

## Assumptions

- the driving seam is Qwen Code's ACP surface (qwen --acp / --experimental-acp, stdio JSON-RPC), NOT the headless CLI (qwen -p -o stream-json): the bridge acts as ACP client, Qwen Code as agent; this is the operator's stated decision (provenance: this session's instruction; qwen 0.22.0 cli.js probes the --acp flag and the acpAgent chunk carries initialize/protocolVersion/agentCapabilities)
- the fleet can run qwen today, measured 2026-08-23: spark, thor and orin all carry qwen 0.22.0 under ~/.local/lib/qwen-code; model identity is host-local (spark+thor: unsloth/Qwen3.8-27B-NVFP4, orin: cortex - slower, less context, per operator), so input.model stays optional and the capability surface reports the host's model + context budget instead of assuming one (provenance: ssh probes + ~/.qwen/settings.json model.name on all three hosts)
- one qwen --acp process per invocation, mirroring the sibling exec model; the measured dual-session capability (two sessions served in one process) stays unused in the first cut; continuation across invocations rides on session/load - agentCapabilities.loadSession is true in the measured initialize response - which is the concrete shape park v2 must measure (provenance: challenge probe2, 2026-08-23)

- [unknown_nonblocking] craft/drainMidTurnQueue semantics: measured twice (probes 1 and 2) with the empty-result answer accepted and the prompt completing normally, but the todoStopGuardWatchQueuedPrompt parameter implies a mid-turn queued-prompt mechanism the bridge would silently drop; validate the real handler contract before the bridge relies on mid-turn queueing (lenient unknown-ext handling stays the first-cut behavior per the v1 decision)

## Resolved vagueness

- [unknown_blocking] ACP client-request direction is unverified: the qwen 0.22.0 bundle carries `request_permission` / fs/`read_text_file` / terminal/create strings, but whether the ACP agent SENDS them to the client (the bridge must then implement fs + terminal JSON-RPC handlers) or handles its own tools in-process (bridge only answers session/`request_permission` + session/cancel) is unmeasured; resolve with a live initialize + session/new + session/prompt probe before the spec lands — resolved: measured by a live ACP probe (qwen 0.22.0, scratch cwd, 2026-08-23): qwen's ACP agent runs its own tools IN-PROCESS - the shell tool call surfaced as `tool_call` / `tool_call_update` session/update notifications and NO fs/`read_text_file`, fs/`write_text_file`, terminal/\* or session/`request_permission` request reached the client; the only agent-to-client request observed was the qwen-specific ext method 'craft/drainMidTurnQueue' (answering it with an empty result lets the prompt complete normally). So the bridge as ACP client implements initialize / session/new / session/prompt / session/cancel plus lenient unknown-ext handling, and classifies the session/prompt response {stopReason, error} as the terminal event - no fs or terminal JSON-RPC handlers are needed for the first cut; a session/`request_permission` handler is added only if the constrained-approval policy (park v3) turns out to route permissions to the client. Bonus grounding for v2: the terminal response carries `_meta`.qwen.branchPoint {assistantRecordUuid, checkpointUuid} - qwen's resume/branch handle.
