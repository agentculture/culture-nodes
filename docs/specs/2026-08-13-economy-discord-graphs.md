## Assumptions

- The designed in-process hook (events.EventSink on the outbox Relay, internal/events/relay.go:26) is wired into no binary today — nothing constructs a Relay in cmd/ — and a sink runs inside the batch transaction, so if it were used for notifications it must enqueue-and-return; the SSE daemon path avoids standing the Relay up at all
- Parallel-token groundwork exists but is unhonored (#43): limits.maxParallelTokens is read, defaulted to 1, and carried (internal/engine/workflow.go:77) yet the engine runs exactly one active token (engine/doc.go:46-53); token rows already carry parent links and `signal_subscriptions` (migration 0016) already permit multi-waiter subscription — split/join and any-node event pickup are the missing pieces
- The nudge/reply-relay leg of #41 is a separate transport from the webhook: the webhook is outbound fire-and-forget only, while discord-bot-cli (/home/spark/git/discord-bot-cli, the 'discord-cli' issue #41 names) is bidirectional but strictly one-shot and poll-based — no gateway listener, no DM verb — so the tracker owns the cadence: thread create per parked attempt + thread post nudges + channel messages polling for the human's reply; nothing upstream provides rate limiting, and steward's discord-notify skill has the severity-color/username/timestamp embed vocabulary worth lifting for escalating nudges
- A single-workflow graph renderer already exists to build on: React Flow + dynamically-imported ELK layout with deterministic fallback (hooks/useElkLayout.ts) + parseWorkflowGraph over one IR's spec.edges (domain/graph.ts) — but #56's cross-workflow 'known Node Graphs' joined by handovers and announced/consumed events has NO data source: there is no /v1alpha1/nodes endpoint, node definitions live only inside workflow-version IRs, and node-announced/consumed events have no schema at all today
- The #45 dashboard substrate already exists as ledger projections: the PRD §10.9 set (`ready_tasks`, `active_tasks`, `verification_queue`, `decision_history`, `delivery_summary`, `open_assumptions_and_questions`, `confirmed_claims`, `current_scope`) is served per run and rendered today only inside the per-run LedgerView picker; authority levels + AuthorityChip already encode system-knows vs user-reports visually
- The bridge config surface budget work builds on: `always_async`, `sync_max_steps`/`decide_async`, and two refusal precedents (503 `actor_unavailable` version gate, 403 allowlist) exist field-for-field across the three bridges; nothing exists for concurrency caps, in-flight limits, pacing, capacity/quota state, budget ceilings, or git-preserve policy — `async_runner`.start() spawns unbounded
- Budget accounting distinguishes cold starts from resumed turns: budget.`max_sessions` counts NEW provider sessions, and a resumed warm turn charges differently — otherwise stickiness (c3) and the economic contract (c6) fight each other, since a workstream of N node turns on one warm session would count as N sessions and always exhaust the budget it was designed to conserve
